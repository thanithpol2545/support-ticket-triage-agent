# 2.1 ชุดประเมินนำร่องจากข้อมูลภายนอก

## คำถามประเมินและวิธีคัดเลือก

**เมื่อข้อความภาษาอังกฤษกล่าวถึงการชำระเงินด้วยบัตร ระบบระบุประเภทปัญหาใน `issue_types` ได้ละเอียดพอที่จะแยกค่าธรรมเนียม รายการที่ผู้แจ้งไม่รู้จัก รายการที่ถูกปฏิเสธ และรายการที่ยังค้างหรือไม่?** กำหนดคำถามก่อนเลือก dataset และกำหนดโควตา 4 ตัวอย่างต่อ intent ก่อนเปิดอ่านแถวที่สุ่มได้ โดยใช้ test split และคงทุกแถวที่เลือกไว้ใน pilot แม้ข้อความจะกำกวม

1. อ่าน CSV ที่ revision ด้านล่างด้วย `csv.DictReader` แล้วให้เลข record `n` เริ่มจาก 1 หลัง header ใช้ `category` แบ่งเป็น 4 กลุ่มตามตาราง mapping
2. คำนวณ `sha256(f"ooca-external-pilot-v1:{n}".encode("ascii")).hexdigest()` ให้แต่ละแถวใน 4 กลุ่ม เรียงจากค่าน้อยไปมากแยกกลุ่ม ใช้ `n` ตัดสินกรณีค่าแฮชเท่ากัน และเลือก 4 แถวแรกต่อกลุ่ม จากนั้นรวมทั้ง 16 แถวแล้วเรียงตาม `n` เพื่อรักษาลำดับต้นทาง
3. ตรวจข้อความทุกแถวที่เลือกก่อนนำเข้า พบข้อความครบ 16/16 แถวและไม่ซ้ำกัน จากการอ่านทีละแถวไม่พบชื่อที่ระบุบุคคลได้ ข้อมูลติดต่อ เลขบัตร หรือเลขบัญชี เก็บแถวกำกวม 2 แถวไว้โดยติดสถานะรอตรวจ label และไม่สุ่มทดแทน

ตรวจพบ 3,080 แถวใน test split, 77 intent และ 40 แถวต่อ intent สำหรับสี่กลุ่มที่กำหนด โควตาเท่ากันใช้เปรียบเทียบ intent ที่อยู่ใกล้กัน ตัวเลขจาก pilot จึงสะท้อนเฉพาะตัวอย่างที่คัดตามโควตานี้

## ชุด Ticket และค่าทางเทคนิค

[ไฟล์ Ticket JSON ทั้ง 16 ตัวอย่าง](../evaluation/banking77-pilot-tickets.json) ใช้ schema ของ repo โดยนำ CSV `text` ไปใส่ใน `messages[0].text` แบบอักขระต่ออักขระ ไม่มีการแปลหรือเขียนข้อความใหม่ CSV มีหนึ่งข้อความต่อแถว จึงไม่มี turn อื่นให้เพิ่ม

| Field | ค่าและความหมาย |
|---|---|
| `ticket_id` | `B77-TEST-<เลข record สี่หลัก>` สำหรับ join ผลกับตาราง |
| `customer.customer_id` | `EXT-` ตามด้วย ticket ID เป็นรหัสนำเข้าที่สร้างขึ้นใหม่ |
| `customer.plan`, `customer.tenure_months` | `"unknown"`, `0` เป็นค่าทางเทคนิคสำหรับ field บังคับ อายุสมาชิกจริงไม่ทราบ |
| `customer.region`, `customer.seats`, `customer.notes` | `null`, `null`, `""` เพราะต้นทางไม่มีข้อมูล |
| `messages[0].when` | `"unknown"` เป็นค่าทางเทคนิคสำหรับ field บังคับ ต้นทางไม่มีเวลา |

กำหนด expected result จาก `category` และตรวจความสอดคล้องกับ `text` เท่านั้น ค่าทางเทคนิคและผลจาก mock tools ไม่ใช้เป็นหลักฐานเฉลย สถานะธุรกรรม ยอดเงิน การคืนเงิน และผลกระทบที่ปรากฏเป็นข้อมูลตามที่ผู้เขียนข้อความระบุ

| Metric ของ external pilot | พร้อมใช้ | ใช้ให้คะแนนแล้ว | วิธีคิดเมื่อรัน |

**ยังไม่ได้รัน GPT** สภาพแวดล้อมตรวจงานไม่มี `OPENAI_API_KEY` ยืนยันแล้วว่า Ticket ทั้ง 16 รายการผ่าน schema สองแถวอยู่ในสถานะ **รอตรวจ label** และยังไม่มีผู้ตรวจที่เป็นคน การตรวจนำเข้าไม่มีคะแนนโมเดล

1. ถ้าจะนำสองแถวที่ค้างมาให้คะแนน ให้ผู้ตรวจอ่านต้นฉบับและเกณฑ์ก่อนรัน GPT ตรวจว่าข้อความมีหลักฐานรองรับ intent ใด บันทึกชื่อผู้ตรวจ วันที่ เหตุผล และทุกผลที่ยอมรับได้ ถ้าข้อความรองรับเฉพาะประเภทกว้างหรือหลักฐานยังไม่พอ ให้คงแถวนั้นไว้นอก metric แบบเทียบ label ต้นทาง
2. ใช้คำสั่ง `verify`, `prepare` และ `score` ตามรายงานวิธีรันซ้ำ รัน CLI ด้วย `--audit` เพื่อเก็บรุ่นโมเดล ข้อเสนอก่อน Policy ผลสุดท้าย และเครื่องมือจากการรันเดียวกัน [วิธีรันซ้ำ](evaluation-results.md)
3. ให้ 1 คะแนนเมื่อพบ label ต้นทางหรือคำพ้องที่ล็อกไว้ในอย่างน้อยหนึ่งค่าใน `issue_types` หลัง normalize ให้ 0 เมื่อมีแต่หัวข้อกว้างอย่าง `billing` หรือไม่มีประเภทที่คาดไว้ คำพ้อง `card transaction rejected` ตรงกับการถูกปฏิเสธ ใน 1627 ถ้ามีเพียงรายการซ้ำโดยละสถานะค้าง จะถูกนับเป็นเคสที่ไม่ตรง รายงานแสดงผลถูก/แถวที่ให้คะแนนได้ แถวที่ไม่มีผลแสดงแยก และสองแถวรอตรวจไม่นำเข้าตัวส่วน [rubric ที่ล็อกไว้](../evaluation/banking77.py)

รายงานแยก pilot จาก [สาม ticket ของ OOCA](../src/triage_agent/data/tickets.json), [ชุด regression สังเคราะห์ 9 fixtures](../evaluation/adversarial_cases.json) และ [ชุด 24 เคสแบบคู่](../evaluation/paired_cases.json)

## ข้อมูลจากภายนอกช่วยทดสอบอะไรที่ชุดเดิมยังพิสูจน์ไม่ได้

ชุดนี้เพิ่มการทดสอบการจำแนก intent ภาษาอังกฤษจาก benchmark ที่ผู้จัดทำภายนอกกำหนดหมวดไว้ล่วงหน้า โดยตรวจว่าระบบจับความต่างของรายละเอียดในหัวข้อการจ่ายเงินได้เมื่อเจอถ้อยคำที่ผู้ทำเคสของโปรเจกต์ไม่ได้เขียนเอง เคสต่อไปนี้ให้หลักฐานที่ใช้ตรวจประเด็นดังกล่าวได้เมื่อรันจริง

- **`B77-TEST-0833` เทียบกับ `B77-TEST-0817`** แถวแรกถามหลักเกณฑ์ค่าธรรมเนียม แถวหลังบอกว่าเห็นค่าธรรมเนียมหลังจ่าย ทั้งคู่ใช้ label เดียวกัน จึงตรวจได้ว่าระบบระบุหัวข้อเดียวกันได้ทั้งในคำถามทั่วไปและรายงานเหตุที่เกิดแล้ว ผลนี้ให้คะแนนเฉพาะหัวข้อ หากจะวัดว่าแยกคำถามออกจากเหตุที่เกิดแล้วได้หรือไม่ ต้องมีเฉลยอีก field ที่แยกสองลักษณะนี้
- **`B77-TEST-1627`** คำถามเน้นรายการซ้ำและการคืนเงิน แต่ label จากต้นทางวัดการพบสถานะค้างในรายการที่สอง จึงตรวจได้ว่าระบบเก็บรายละเอียดสถานะการชำระเงินไว้ใน `issue_types` เมื่อข้อความเดียวมีหลายประเด็น
- **`B77-TEST-1815`** การจ่ายด้วยบัตรไม่ได้อาจเกิดได้หลายแบบ ขณะที่ต้นทางระบุว่าถูกปฏิเสธ เคสนี้แสดงจุดที่ความละเอียดของ label เกินหลักฐานในข้อความและต้องให้คนตรวจ หากให้คะแนนทันที ระบบที่รายงานอาการตามข้อความอาจถูกนับว่าผิด

ผลในอนาคตจะอธิบายความสามารถเฉพาะ intent และตัวอย่างที่ใช้ ชุดนี้ใช้โดเมนธนาคาร ภาษาอังกฤษ และข้อความเดี่ยว อีกทั้งเป็น benchmark สาธารณะที่อาจปรากฏในข้อมูลฝึกของโมเดล หลักฐานสำหรับการตั้ง urgency และ routing ของ OOCA ยังต้องมาจากเคสที่มีบริบทและเฉลยที่ตรงกับงานนั้น
